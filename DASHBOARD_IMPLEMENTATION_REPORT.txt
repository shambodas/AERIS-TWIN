2. FILES CREATED
----------------
- server.py
  A thin HTTP/SSE adapter around the existing EngineSimulator. It maintains one
  simulator instance, accepts validated control commands, broadcasts live state,
  exposes bounded history, and optionally republishes telemetry through the
  existing MQTT publisher.

- web/index.html
  A responsive single-page browser interface with two route-specific views:
  /gcs for judge-facing UAV control and /engine for engine monitoring.

- DASHBOARD_IMPLEMENTATION_REPORT.txt
  This report.

3. FILES MODIFIED

4. EXISTING FILES DELIBERATELY LEFT UNTOUCHED
---------------------------------------------
The existing engine physics, mission, sensor, fault, MQTT, CAN, logger, and
validation modules were left untouched. The dashboard uses them as the source
of truth and does not duplicate engine calculations in browser code.

5. FRONTEND TECHNOLOGY
----------------------
- Plain HTML, CSS, and browser JavaScript.

6. COMMUNICATION ARCHITECTURE
-----------------------------
Browser GCS and Engine Monitor
        |
        | HTTP commands and Server-Sent Events
        v
server.py adapter
        |
        | EngineInputs and EngineSimulator.step()
        v
Existing Python engine physics and sensor model
        |
        +--> browser telemetry state
        +--> optional existing MQTT telemetry publisher

Both browser routes connect to the same server process and simulator instance.
The adapter binds to 0.0.0.0 by default, so it can be reached over a LAN.

7. MQTT TOPICS
--------------
The existing telemetry topic was reused:

- aeris-twin/engine/telemetry

MQTT publishing is disabled by default for development. Enable it with:

  AERIS_MQTT=1
  AERIS_MQTT_HOST=<broker-host>
  AERIS_MQTT_PORT=1883

The current browser command path is HTTP POST /api/command. A future command
bridge can publish the same validated command schema to an MQTT command topic.
No redundant MQTT topic was added.

8. LIVE STATE SCHEMA
--------------------
The adapter emits a JSON state containing:

- uav: status, altitude_m, speed_mps, heading, progress
- engine: status, rpm, cht_c, oil temperature, oil pressure, vibration,
  fuel flow, throttle, load, torque, and intake pressure
- digital_twin: synchronization status, telemetry rate, simulation time,
  rule-based health percentage, active fault, and severity
- mission: id, name, key, phase, progress, elapsed time, running, and paused
- alerts: current rule-based operator alerts
- telemetry: complete measured SensorState fields
- events: recent command/system events

The measured engine values come from the existing SensorModel. The simulator
remains authoritative.

9. COMMAND SCHEMA
-----------------
Commands are sent as:

  {
    "command": "start_mission",
    "parameters": {"mission": "hot_weather"}
  }

Supported commands include:

- start_mission
- start_uav
- stop_uav
- pause_uav
- reset_simulation
- set_altitude
- set_speed
- set_heading
- inject_fault
- clear_fault

Mission names, fault names, numeric ranges, and finite numeric values are
validated before reaching the simulator. Unsupported throttle control is
rejected because throttle currently follows MissionProfile inputs rather than
being independently exposed by the adapter.

13. HOW TO START
----------------
From the repository root:

  python server.py

The server prints:

  http://localhost:8080/gcs
  http://localhost:8080/engine

Open both URLs in separate browser tabs on one computer. For a second device,
use the host computer's LAN address, for example:

  http://192.168.x.x:8080/gcs
  http://192.168.x.x:8080/engine

The host firewall must permit the selected port. The Python adapter is bound
to 0.0.0.0 by default and can be configured with AERIS_HOST and AERIS_PORT.

15. LIMITATIONS AND ASSUMPTIONS
--------------------------------
- The current adapter is a prototype HTTP/SSE bridge, not a production API.
- Browser command traffic is not yet published to MQTT; only telemetry can be
  optionally republished through the existing MQTT publisher.
- The simulated UAV position uses mission progress and a visual route; the
  existing engine project does not provide real latitude/longitude flight
  dynamics.
- Heading is currently a dashboard/UAV visualization control and is not an
  engine physics input.
- Throttle remains mission-profile controlled because the existing simulator
  does not expose an independent runtime throttle command in this adapter.
- Mission profiles reuse the existing default MissionProfile and apply small
  scenario overrides where available; these are integration-layer operating
  inputs, not a second engine model.
- History and replay currently use an in-memory bounded buffer of 600 samples.
  Existing generated CSV files were not rewritten or replaced.
- The condition score is a transparent rule-based telemetry score and is not
  an ML prediction.
- No ML model was trained or implemented.
- No real hardware sensor data is claimed.

16. FUTURE INTEGRATION POINTS

FINAL STATUS
------------
The current prototype provides a shared-source GCS and Engine Monitor vertical
slice around the existing Python Digital Twin. Commands flow into the existing
simulator, telemetry flows out to both views, supported faults affect the real
fault models, and ML remains an explicit future service boundary.
